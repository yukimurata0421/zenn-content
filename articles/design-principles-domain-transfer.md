## はじめに

この記事は、各リポジトリの詳細を紹介する記事ではありません。

書きたいのは、あるドメインで有効だった設計原則を別のドメインへ移植したときに、何が不変で、何が新たな設計問題として立ち上がるのか、という話です。

私は、ADS-B 受信環境の改善を統計的に評価する **ARENA**、Gmail から Discord への通知パイプラインである **amazon-notify**、Raspberry Pi 上のサービスを監視し段階的に回復させる **raspi-sentinel** を作ってきました。対象は異なりますが、障害・状態・処理境界という観点では同型の問題を扱っています。

結論を先に言えば、設計原則は再利用できます。
ただし、バッチ評価基盤から通知・監視のような常駐系へ移ると、時間軸・状態遷移・自動化の影響範囲が前景化し、追加で設計しなければならないものが増えます。

---

## 最初のドメインで確立した不変原則

ARENA は、ADS-B 受信環境の改善を統計的に評価する基盤です。現在は **Pipeline / Artifacts / Synthesis** の 3 つの subsystems を持ちます。

- **Pipeline**: データ処理と統計評価を実行する
- **Artifacts**: 出力を AI レビューや再検証向けに構造化・パッケージングする
- **Synthesis**: AI 出力やレビュー結果を、後から再確認できる形で保持する

ただし本稿で、設計原則の起点として主に扱うのは **Pipeline** と **Artifacts** です。ここで形になった判断基準が、後の別ドメインにも移植されました。

この開発を通じて、少なくとも 4 つの不変原則が固まりました。

### 原則 1: 成功を確認する前に状態を進めない

出力ファイルが存在していても、中身が空、サイズが異常、入力依存ファイルより古い、といった状態なら成功とはみなしません。
return code 0 をそのまま信用せず、**期待した結果が本当に成立したか** を見ます。

### 原則 2: 障害を隠さず可視化する

必要な成果物が欠けていれば欠落として残し、コピーに失敗すれば失敗として残します。
障害を吸収して「なんとなく成功っぽく見せる」より、**壊れ方を見えるまま残す** ことを優先します。

### 原則 3: 正本は append-only で、事後検証可能にする

実行ログは append-only に記録し、成果物は manifest や provenance とともに保持します。
さらに SHA-256 を付けて、**後からその時点の内容を検証できる** ようにします。

### 原則 4: 手法そのものを疑う

統計モデルが数字を出したからといって、それをそのまま真実とは扱いません。
複数手法の一致は defensible の材料になりますが、**不一致そのものも検証対象** です。
AI の出力も同じで、結論ではなく仮説として扱います。

## 別ドメインへ移植した背景

### raspi-sentinel

きっかけは、Raspberry Pi 上の ADS-B 関連サービスが停止し、数時間分のログが欠けたことでした。

ただし問題は、単にプロセスが落ちたことではありません。`systemd` の `Restart=always` では、プロセスの生死しか扱えず、**プロセスは生きているが意味上は停止している** という障害クラスを扱えなかったことです。

そこで必要になったのが、process health ではなく **semantic health** を評価する監視でした。

### amazon-notify

Amazon の配送メールを Discord に通知する仕組みです。
ここでの問題は、通知失敗そのものよりも、**失敗したメールが永久にスキップされること** でした。

必要だったのは速度の最大化ではなく、**処理境界を壊さずに前進すること** でした。

## ドメインが変わると何が追加で必要になるか

ARENA の中心は、常駐ループではなく **run 単位の離散実行** です。監査ログや成果物、Synthesis の DB は永続化されますが、監視系のように長寿命プロセスが内部状態を抱え続ける設計ではありません。

一方、通知や監視では **時間軸と状態遷移** が支配的になります。
不変原則はそのまま適用できますが、制約が変わることで新たな設計問題が現れます。

先に対応表を示します。

| 不変原則 | ARENA での現れ方 | 通知・監視での現れ方 |
|---|---|---|
| 成功を確認する前に状態を進めない | output contract check | ordered frontier / guarded state advance |
| 障害を隠さず可視化する | FAIL_OUTPUT / manifest の欠落記録 | semantic health / status と reason の分離 |
| 正本は append-only で事後検証可能 | append-only audit log と artifact verification | events.jsonl を正本とした書き込み順序契約 |
| 手法そのものを疑う | 複数統計手法・AI 出力を仮説として扱う | 自動 restart / reboot に多重ガードを置く |

以下、各差分を「不変原則 → 新しい制約 → 追加設計」の順で整理します。

### 差分 1: checkpoint をどこまで進めるか

**不変原則:** 成功を確認する前に状態を進めない

**新しい制約:** 常駐アプリでは、処理が途中で止まっても次回実行へ状態が持ち越される

**追加で必要になった設計:**

ARENA では、run が終わればその run 単位で結果が確定します。
しかし amazon-notify では、メール 1 通ごとに成功・失敗が分かれます。

たとえば、メッセージ A の通知に成功し、メッセージ B の通知に失敗した場合を考えます。

```text
1. メッセージ A 通知成功 → checkpoint は A へ進む
2. メッセージ B 通知失敗 → run は B で停止
3. checkpoint は A のまま（穴を作らない）
4. 次回 run は B から oldest-first で再開
```

これが ordered frontier です。

原則自体は同じです。
違うのは、成功確認の粒度が「run 全体」から「1 メッセージ」へ細かくなり、**停止位置と再開位置を設計対象として明示しなければならなくなった** ことです。

### 差分 2: 正本と派生物の書き込み順序

**不変原則:** 正本は append-only で、事後検証可能にする

**新しい制約:** 常駐アプリでは正本以外に互換スナップショットや補助的な派生物が存在し、更新順序が整合性に影響する

**追加で必要になった設計:**

ARENA の audit log は、基本的に append-only の単一系列として扱えます。
一方 amazon-notify では、checkpoint の正本が `events.jsonl` にあり、互換スナップショットとして `state.json`、run 単位の監査ログとして `runs.jsonl`、さらに再生成可能な index が存在します。

ここで問題になるのが書き込み順です。

もし派生物を先に更新し、正本の記録に失敗すると、**派生だけが進み、正本が遅れる** という不整合が起きます。

そこで、書き込み順序を契約として固定しました。

1. `events.jsonl` に `checkpoint_advanced` を追記する（正本）
2. `state.json` などの派生物を best-effort で更新する
3. index は必要なら再構築する

ARENA では前景化しなかった **正本・派生・補助データの一貫性** が、常駐アプリでは明示的な設計対象になります。

### 差分 3: 「プロセスは生きているが実質停止」という障害クラス

**不変原則:** 障害を隠さず可視化する

**新しい制約:** 常駐プロセスでは、return code も process alive も、障害の不在を証明しない

**追加で必要になった設計:**

ARENA では、出力の欠落や stale な成果物を検出することで、失敗をかなり明確に扱えます。
しかし raspi-sentinel が対処するのは、もっと曖昧で継続的な障害です。

- systemd から見れば `active` だが、出力更新が止まっている
- DNS は引けないが、ゲートウェイ疎通はある
- 壁時計に異常があるが、プロセス自体は生きている
- `stats.json` の入力時刻は進むが、成功時刻が止まっている

ここでは「return code を信用しない」が、「process alive を信用しない」に変換されます。

その結果、raspi-sentinel では `status` と `reason` を分離しました。
重要なのは failed かどうかだけでなく、**なぜ failed なのか** です。

reason は `dns_error` / `gateway_error` / `stats_stale` / `clock_frozen` などとして分離されます。
たとえば `dns_error` 単独では即 reboot の理由にはなりません。
同じ failed でも、依存関係の一時障害なのか、semantic な出力停止なのか、時計異常なのかで、取るべき recovery action は変わります。

### 差分 4: 自動化の境界を影響範囲で決める

**不変原則:** 手法そのものを疑う

**新しい制約:** 常駐アプリの自動化は、想定の斜めに行ったときに他のシステムまで巻き込む

**追加で必要になった設計:**

ARENA では、統計モデルや AI 出力を結論として受け入れず、**監査可能な仮説** として扱う設計を取りました。

raspi-sentinel でも、同じ問題が別の形で現れます。
自動 restart や reboot は技術的には簡単にできます。しかし、検知が少しでもずれていれば、復旧行動そのものが新しい障害源になります。

だから、自動化の境界は「できるかどうか」ではなく、**誤判定時の影響範囲** で決めなければなりません。

そのため raspi-sentinel では、reboot に複数の guard を置いています。

- 最小 uptime 経過前は reboot しない
- cooldown window 内の連続 reboot を禁止する
- rolling window 内の reboot 回数に上限を設ける
- 時計異常では、複数シグナルの整合が取れたときにだけ reboot を許可する

ARENA で言えば「AI output は hypothesis であって conclusion ではない」。
raspi-sentinel で言えば「自動 reboot は仮説に基づく行動であり、確証なしには実行しない」です。

## 移植プロセスの構造

振り返ると、移植のプロセスは毎回ほぼ同じ構造を取っていました。

### 1. 分岐を洗い出す

まず、そのシステムで何が起こりうるかを分岐として列挙します。
バッチ実行にはなかった、状態の持ち越し、外部依存の変動、長期生存プロセス特有の不整合を洗います。

### 2. 意味改変かどうかで自動化境界を引く

ARENA の Synthesis では、構造だけを直す修復と、意味を変えうる修復を分けて扱います。
この考え方は別ドメインでも有効でした。

amazon-notify でも、transient failure のリトライは自動化できますが、checkpoint の前進は成功確認後にしか許しません。
重要なのは、「自動化できるか」ではなく、**その操作が意味改変を伴うかどうか** です。

### 3. 実際に運転して、想定外を概念に還元する

開発環境や実運用では、想定外が必ず起きます。
そのとき個別事象にその場しのぎで対応するのではなく、背後にある概念を抽出して設計原則へ返します。

たとえば amazon-notify では、永続化の失敗が frontier や通知導線そのものを壊さないようにする、という原則が必要になりました。
ordered frontier と runtime artifacts の設計は、その原則の具体化です。

必要に応じて、LLM を補助的に使い、自分の想定にない分岐を洗い出すこともあります。
ただし、その出力も仮説として扱い、最終的には自分の設計原則に照らして取捨選択します。

## 設計原則は変わらない。差分だけが変わる

3 つのリポジトリで使っている技術は、どれも既存のものです。
Python、systemd、JSONL、SHA-256、Gmail API、Discord Webhook。新しいフレームワークが本質なのではありません。

やっていることは、最初のドメインで確立した設計原則を別のドメインに持っていき、制約差分を洗い出し、その差分に対して設計を追加しているだけです。

私が作っているのは、個別のツールではありません。
障害・状態・処理境界をどう扱うかという設計原則の実装例です。

原則は同じ。差分だけが変わる。
