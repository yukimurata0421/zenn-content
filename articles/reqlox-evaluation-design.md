REQLOXでは、対応するPython構造と所有者要件を固定し、故障検出から修復候補の再注入・正常回帰までを検査している。その実装と実測結果は[主記事](https://zenn.dev/north_to_now/articles/reqlox-failure-knowledge-qualification)にまとめた。

本記事で扱うのは、原文の解釈から修復結果までの、各段階の評価をどう設計したかである。修復候補が固定条件を通ること、生成内容が原文に支えられること、外部知識を与えた寄与があることには、それぞれ別の証拠が必要になる。

Sourceは障害報告などの入力資料、Targetは検証対象のコードを指す。結果は2026年10月9〜21日JSTの保存記録に基づく。主な問いと現在地は次のとおりである。

| 評価するもの | 必要な比較・根拠 | 保存記録で分かったこと |
| --- | --- | --- |
| 原文の主張の支持 | 引用区間と、命題・関係に対する独立した判断 | 引用一致と主張の支持を別の結果として記録する。自然Sourceに対する独立labelでの精度は未測定 |
| Targetへの適用可否 | 対象側事実と故障の成立条件 | 保存済み7判断はすべて情報不足で、適用候補0件 |
| 確率出力の比較 | 共通参照、真値label、欠測を含めた分母 | 自然Source 3件・40参照のpaired Brier差は、すべて0を含む |
| 新規生成の反復安定性 | 同じ入力・requestに対する新しい生成 | 3回の固定基準による総合判定はNOT_STABLE |
| Sourceの追加価値 | 同じ条件下のSourceなしplanner | 実Targetの比較は対象条件が成立せず、効果は未測定 |

# 1. 原文の支持と、Targetへの適用可否を分ける

IRの生成では、原文の引用区間を保存し、命題と関係をその区間に結び付ける。offsetとhashがあれば、別の段落の引用に差し替えた入力を同じ根拠として扱ってしまう誤りは防げる。

ただし、引用が原文に存在することと、その引用が主張を支持することは別の問題である。原文に障害Aと障害Bが並んでいるだけなのに「AがBの原因」という関係を付ければ、引用の文字列が完全に一致していても、因果関係は支持されていない。そこで、審査を命題や関係の単位に分け、支持の有無を一つずつ問う。出力形式が正しいか、原文に忠実か、Targetに適用できるかは、それぞれ別の結果として記録する。

実験経路へ条件を渡す側には、根拠区間を保持する有限のprojection（原文から条件を取り出す変換）を置いた。操作名と失敗の表現が同じ段落にあれば条件として取り出し、否定表現、複数の操作の混在、発生したphaseを特定できない場合は保留にする。これは対応する操作語と失敗語を定義した有限の文法であり、自然文を自由に解釈して未知の故障機構を作り出すものではない（[条件projectionの実装](https://github.com/yukimurata0421/REQLOX/blob/17866ed918753b18bfacdc0b7ced06c6dd7c4e2e/reqlox_core/reliability_source_conditions.py)）。

対象の構成を表すSystem IRは、既存のschema付きevidence-lineage graphを変換する対応adapterで生成する。snapshot内のコード参照はASTまたは明示したtext windowで添え、再生成した値を保存済みのwitnessと照合する。任意のコードからarchitecture全体を自動推定する処理は、この経路の実装範囲に含めていない。

Target側のSystem IRについても、二つの問いを分ける。各要素が根拠に忠実かという問いと、Failure IRが前提とする故障がSystem IRの上で成り立つかという問いである。保存済みの適用可否判断7件を再処理した結果は、7件すべてが`INSUFFICIENT_INFORMATION` / `HUMAN_ON_EXCEPTION`で、適用候補は0件だった。入力と後処理を再現できても、適用に必要な事実が足りなければ、実験の候補は増えない（[System IRの再現経路と検証範囲](https://github.com/yukimurata0421/REQLOX/blob/17866ed918753b18bfacdc0b7ced06c6dd7c4e2e/docs/system-ir-reproduction.md)）。

# 2. 未確定labelを分母に残す：paired Brier区間

意味の評価で難しかったのは、自然な障害報告に付けられた独立の正解labelが十分にないことである。審査器の回答を正解とみなすと、審査器が自分自身と一致した度合いを精度として報告することになる。

そこで評価器では、labelや確率vectorが欠けた行も捨てずに残し、Brier scoreとlog lossが取り得る範囲を計算する。categorical Brierの定義は次のとおり。

$$
L(p, y) = \sum_k \left(p_k - \mathbb{1}[y = k]\right)^2
$$

labelが不明でvectorが分かっている場合は、取り得るlabelごとに損失を計算し、その最小値と最大値を残す。旧方式と後継方式を比べるときは、同じ参照に対する未知のlabelを、両方式で共有させる。

$$
\Delta_{\min} = \min_y \left( L(p^{\mathrm{succ}}, y) - L(p^{\mathrm{base}}, y) \right), \quad
\Delta_{\max} = \max_y \left( L(p^{\mathrm{succ}}, y) - L(p^{\mathrm{base}}, y) \right)
$$

二つのscore区間を別々に求めてから単純に引き算すると、未知のlabelを両側で独立に動かすことになり、区間が必要以上に広がる。labelを共有すれば、比較に必要な対応関係を保てる。たとえば同じvector同士なら、labelが不明でも差は0になる。

保存済みの自然なSource 3件（計40参照）で診断すると、paired差は次の範囲になった。差は「後継 − 旧」で、負の値なら後継の損失の方が小さい。

| Source | 共通参照数 | paired Brier差の取り得る範囲 |
| --- | ---: | ---: |
| A | 11 | −0.1648〜+0.3426 |
| B | 10 | −0.3320〜+0.3860 |
| C | 19 | −0.5078〜+0.4132 |

三つとも0を含むので、この証拠からは改善したのか悪化したのかを確定できない。なお、この範囲はlabelが確定していないことから生じる幅であり、標本のばらつきに対する95%信頼区間ではない。

labelやvectorが欠けた行を除いて平均を取ると、観測が得られた部分に条件付けた値になる。そこで、採点可能な部分の値と、全分母に対する取り得る範囲を分けて残す。欠測を都合のよい正解へ補ったり、確率vectorを正規化して結果を書き換えたりはしない。

この評価器を入れたことで、採点できた部分の平均だけが良くなった場合に、全体として改善したと言えるかどうかを別に検査できるようになった。残る課題は、自然なSourceに対する独立のlabelを用意することと、Source間の依存を考慮した評価設計である。

# 3. replayと、新規生成の安定性を分けて測る

replayでは、原文、生成plan、保存したrequest、保存したresponse、schema、policy、実装を結び付け、requestをbyte列まで照合したうえで後処理を再実行する。質問IDが同じでも、入力が違えば拒否する。replayは、新たなprovider呼出しもTargetの実行も行わない（[replayの実装](https://github.com/yukimurata0421/REQLOX/blob/17866ed918753b18bfacdc0b7ced06c6dd7c4e2e/reqlox_knowledge/pipeline.py)）。

replayで確かめられるのは、保存済みの応答を同じ処理に通せることだけである。新しく生成し直したときの安定性は、別に測る必要がある。`temppath`の開発実験では、同じ入力と同じrequestのbyte列を使い、前の回の出力を渡さずに3回生成した。安定性の判定には、次の6層のJaccard係数を使った。

| 比較する集合 | run 1–2 | run 1–3 | run 2–3 |
| --- | ---: | ---: | ---: |
| 引用されたsymbol | 1.00 | 1.00 | 1.00 |
| 引用された行・呼出し | 1.00 | 0.33 | 0.33 |
| 要件の分類・symbol・根拠path | 0.33 | 1.00 | 0.33 |
| 仮説のsymbol・trigger・effect | 1.00 | 0.67 | 0.67 |
| 仮説のsymbol・trigger・effect・site | 1.00 | 0.67 | 0.67 |
| 仮説と要件のlink | 0.20 | 0.67 | 0.00 |

symbolは5件すべてが一致し、`__exit__`での`unlink()`に関する主要な仮説2件も全回に共通していた。しかし、ある回ではcontext managerの要件を一つにまとめ、別の回ではenterとexitに分けていた。周辺的な仮説の有無も回によって変わり、その影響は要件へのlinkにまで及んだ。

事前に決めた基準は「6層すべてのペアでJaccardが0.8以上、かつ重大な判定の反転が0件」であり、総合判定は`NOT_STABLE`だった。なお、分類のenumや候補数の上限が、一致率を押し上げている可能性がある。また、根拠の検査は同じモデルによる1回のbatchで行っており、独立した正解データとの照合や、審査自体の反復は行っていない。

この結果から、二種類の差を分けて評価する必要があることが分かった。文字列やIDの正規化で吸収できる差と、命題の分け方や要件との対応関係が変わる差である。

# 4. Sourceの追加価値を、どの対照と比較するか

既知のコピーで候補が改善することは確認できた。しかしそれだけでは、外部の障害知識を与えたことが何に効いたのかは分からない。候補の生成器がすでに修復方法を持っていて、両armが同じ故障条件を全探索するなら、最終的な発見数も採用も同じになり得るからだ。

そこで、比較の問いを次の形に絞った。

> 対応済みの有限な故障空間で、Sourceは、Targetの情報を使えるSourceなしのplannerよりも、少ない探索で有効な反例に到達させるか。

## Sourceなしの対照にも、Targetの情報を与える

主な対照の`TARGET_GUIDED_SOURCE_BLIND_V1`は、Sourceの本文を読まず、Targetの削除構文やloopから条件を優先して選ぶ。固定の汎用条件を使う`FIXED_GENERIC_V1`は、別のrunとして扱う。

両armで、Targetのsnapshot、所有者要件、使える故障primitive、修復方針、確認条件、探索予算をそろえる。Source側にだけ追加のprimitiveや手書きの正解を渡すと、知識の寄与とは別のものを測ることになる。

主指標は、最初の有効な反例が得られたcampaignの番号（`first_fault_campaign`）にした。最終的な発見集合と採用の差は副指標とする。反例に到達しなかった場合は未達として記録し、0 campaignで発見したとは扱わない。

`source_only_discovered_programs`も、比較したplanner同士の差として読む必要がある。一方のplannerが選ばなかった条件をSource側が選んだとしても、その条件が共有primitiveのlibraryに存在しなかったという意味にはならない（[比較の実装](https://github.com/yukimurata0421/REQLOX/blob/17866ed918753b18bfacdc0b7ced06c6dd7c4e2e/reqlox_core/reliability_incident_conditions.py)、[比較範囲の説明](https://github.com/yukimurata0421/REQLOX/blob/17866ed918753b18bfacdc0b7ced06c6dd7c4e2e/docs/source-comparison-scope.md)）。

実在のTargetで比較する前に、合成した結果の列を比較器に与え、次の性質を確かめた。ここでの数値は合成した入力によるもので、実際のSourceの効果を測ったものではない。

| 合成した状況 | 比較器で確認したこと |
| --- | --- |
| 両armが同一 | 固有の発見と採用の差がどちらも0になる |
| 同じFAIL集合を異なる順序で探索 | 最終的な件数の差は0でも、最初の反例は1回目と4回目に分かれる |
| UNKNOWNを含む | 欠測を残し、比較を完了扱いにしない |
| Source側に固有の発見と採用を構成 | 固有の発見と、採用の差1を検出する |

# 5. 実Targetでは、比較の前提を満たせなかった

2026年10月21日の実験準備では、対象の条件を次のように定めた。未使用の公開Python OSSであること、既存のpath-contextモデルに改変なしで適合すること、Sourceの原文を既存のprojectionがちょうど一つの条件programに変換できること。

web検索を2回行った範囲では、これらを同時に満たす対象は見つからなかった。archiveの取得やTargetのコピーには進んでおらず、対象の凍結、故障注入、修復、再注入はいずれも行っていない。native campaignは0回である。

これはSourceの効果が0だったという意味ではない。比較に入る前の適格条件が成り立たなかったので、効果は測れていない。また、この限られた探索で見つからなかったことは、適合するOSSが存在しないことの証明にもならない。

一方で、この停止によって実装上の課題がはっきりした。対応するcallerの構造、Sourceの形式、projectionの条件が同時に成り立つ範囲が狭い。結果を出すためにTargetやSourceを加工すれば、評価の対象が、転用したい外部の知識から、実験者が作った条件へとすり替わってしまう。

# 6. 次の評価で固定する条件

保存記録から確認できるのは、原文との対応を追える実装、未確定labelを残す比較器、同一入力での3回の生成結果、有限planner比較を準備する経路である。それぞれの検査が通ることを、自然な障害知識の横展開が成功した証拠へまとめて昇格させない。

次の評価では、少なくとも次の条件を結果を見る前に固定する必要がある。

- 原文の意味的評価には、生成器や審査器自身の回答から独立したlabelを用意する。情報不足や欠測は、正誤が確定した行と分けて残す。
- 生成の比較では、文字列やIDの差と、命題の粒度・条件・要件とのlinkが変わる差を分ける。分類enumや候補数の上限も一致率へ影響する条件として記録する。
- Source比較では、対象選定規則、共有primitive、Target情報、所有者要件、修復方針、確認条件、予算、arm順序、打切りとUNKNOWNの扱いをそろえる。Sourceの準備に人が使った時間も別に測る。
- 同じSource、Target、機構、生成器を使う反復を独立標本へ数え直さない。少数の既知例での差を一般化するには、依存を考慮した確認群が要る。

現在のSource追加価値と人的負担削減は未測定である。今後は、未使用Targetの選定から、発見、候補、同条件での再確認までを固定した比較へ接続し、どの段階の改善が実際の発見・修復と人の作業へ効いたかを測る。

検出・修復・再注入の具体例と設計判断は、[主記事「障害知識を実行可能な検証条件へ落とす」](https://zenn.dev/north_to_now/articles/reqlox-failure-knowledge-qualification)で追える。
